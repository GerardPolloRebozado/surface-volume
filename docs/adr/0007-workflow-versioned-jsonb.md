# ADR 0007 - Store workflows as immutable JSONB versions, with UUID keys

* Status: **Proposed**
* Date: 2026-11-16
* Deciders: the whole team
* Refines: [ADR 0003](0003-postgresql-database.md)

## Context

ADR 0003 puts workflow configuration in JSONB inside relational tables, but it does not say how a workflow's graph is laid out: the trigger, the reaction nodes, the optional condition and the links. The subject constrains the graph:
- it is linear, with at most one condition that has two non-merging branches
- it must not encode a maximum number of reaction nodes
- it is validated when saved
- runs must show what happened, step by step

The interfaces in `src/workflow/workflow.types.ts` already describe a `Workflow` as `{ trigger, nodes[], links[] }`.

We also need to choose primary keys. The stub `User` model used an autoincrement `Int`, while every TS type uses `string` ids.

## Decision

1. **A workflow's graph is one JSONB document per version** (`workflow_versions.definition`).
   - Saving inserts a new version. Versions are never updated, and a DB trigger enforces that.
   - `workflows.latest_version_id` is what the builder edits. `workflows.active_version_id` is what hooks run.
   - Every run records the `version_id` it executed.
2. **What must be queryable or carry a foreign key is projected out of the JSON** when a version is activated:
   - `workflow_triggers`: the trigger the hook engine schedules and routes
   - `workflow_connections`: every connection the version uses
3. **All primary keys are UUIDv7**, generated by the Prisma client. The one exception is the append-only, internal `audit_logs` and `login_attempts` tables, which use `bigserial`.

### Alternatives rejected

* **Normalized `workflow_nodes` + `workflow_links` tables, each with a JSONB `config`.**
  - Pro: real FKs from every node to its connection.
  - Con: saving becomes a diff of rows. Versioning means copying every node row. Validating the graph needs the whole graph in memory anyway.
  - Con: the builder sends and receives a whole graph, so we would be splitting and reassembling it on every request.
  - The FK benefit is kept through the `workflow_connections` projection.
* **Mutable single JSONB column on `workflows`.**
  - Pro: simplest.
  - Con: editing a workflow would change what past runs appear to have executed, and a save during a running execution would race with it.
* **Autoincrement integer ids.**
  - Pro: smaller and familiar.
  - Con: ids are enumerable in a public API and reveal volumes. They also disagree with the TS contract (`string`).
  - UUIDv7 keeps index locality because the ids are time-ordered.

## Consequences

### Positive

* Run history is exact: a run always shows the graph it ran, even after edits.
* "Retry this run" re-executes the same version.
* Save is one insert, and validation sees the whole graph at once. There is no structural limit on the number of nodes.
* The hook engine queries plain columns (`next_run_at`, `webhook_token`) and never digs into JSON.
* Revoking a connection finds the workflows it breaks through an FK.

### Negative

1. **Projections can drift.** `workflow_triggers` and `workflow_connections` must be rebuilt in the same transaction that moves `active_version_id`. This is one code path, and it is covered by tests.
2. **Version rows accumulate.** Each save is a full copy, but definitions are a few KB. If it ever matters, old unreferenced versions (not active, latest, or used by a retained run) can be pruned.
3. **Changing the definition format requires `schema_version`.** Old versions are upgraded when read, or with an explicit data migration. They are never upgraded silently in place.
4. **UUIDv7 is generated in the application.** Raw SQL inserts must supply ids.
